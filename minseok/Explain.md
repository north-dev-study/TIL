1. id, select-type - 쿼리 구조 파악
	1. 같은 select 문이면 id가 같다, 서브 쿼리 같은게 있으면 달라짐
	2. select-type 도 기본은 simple 이지만 서브쿼리가 있으면 primary, subquery로 나뉜다
2. type
	1. 테이블 접근 방식이다 const(최선) ~ ALL(최악)
3. possible_keys, key
	1. 인덱스 후보와 선택된 인덱스이다.
4. key_len
	1. 인덱스 바이트 길이로 복합 인덱스에서 몇 개 컬럼까지 사용했는지 확인할 수 있다.
5. rows, filtered
	1. 조사할 추정 행 수와 실행엔진에서 필터링할 비율이다.
6. extra
	1. 추가 정보이다.

- show warnnings 를 explain 쿼리 뒤에 붙이면 옵티마이저가 재작성한 쿼리를 표시해준다.

### type
#### 최상
- const
	- 상수처럼 빠르다.
	- Pk, Unique 처럼 매칭되는 행이 최대 1인 경우
- eq_ref
	- 조인에서 const 이다.
	- 인덱스가 Unique 면서 Not Null 이어야 한다
#### 우수
- ref
	- 매칭되는 행이 여러 개 이지만 인덱스를 사용할 때이다
	- 충분히 빠르다.
	- 비 유니크 인덱스의 동등조건 또는 복합 인덱스의 왼쪽 접두사를 사용할 경우
#### 주의
- range
	- 인덱스 사용하므로 상대적으로 효율적이나 데이터의 양이 많으면 느려진다.
	- IN ( ) 조건도 포함한다.
#### 경고
- index
	- 인덱스 풀스캔한 경우이다.
	- Extra 에 Using index가 있으면 커버링 인덱스인 경우이므로 괜찮다.
	- ALL과 비슷하나 인덱스 트리가 보통 테이블보다 작으므로 빠르다. (하지만 랜덤 I/O 주의)
#### 위험
- ALL
	- Full Table Scan
	- key 에 null 이 나타난다.
	- 테이블을 전부 스캔한다 > 모든 컬럼포함 > 크기가 크다
	- 저용량 테이블에선 이것도 빠르다.

### possible Keys
- 사용할 수 있는 인덱스 후보들

### key
- possible keys 에 값이 있지만 key 가 null 인 경우가 있는데 인덱스보다 Full Table Scan이 빠르다고 판단한 경우이다. (랜덤 I/O 때문)
- possible keys 없지만 key 있는 경우가 있는데 이는 커버링 인덱스일 경우이다.

### key len
- 복합 인덱스에서 몇 개 컬럼을 사용했는지 구분할 수 있다.
- varchar 에는 길이 접두사가 있는데 길이가 255를 초과하면 2 byte 이고 이하면 1byte이다.
- key len 계산은 항상 최댓값 기준이다 > 길이 접두사는 항상 2 byte
- null 허용 시 1 byte 추가 된다
- ex) varchar(20) 4 byte * 20 + 2 byte]

### ref
- 인덱스 비교대상이다.
- 비교 대상(매칭값)으로 어떤 값이 사용되었나 보여준다.
- const
	- 고정된 상수
- 데이터베이스.테이블.컬럼
	- 조인한 경우 (선행 테이블 컬럼)
- func
	- 비교 대상이 함수의 연산 결과이거나 내부적 형 변환을 거친 경우
	- 인덱스가 제대로 안 탈 수 있다.

### rows
- 조사항 추정 행의 수
- 측정 값이 일치하는 이유
	- 인덱스 다이브란 작업을 거치는데 이는 실제로 인덱스를 읽어보는 것이다.
	- 동등 비교나 소량 비교일 경우 잘 작동한다.
- 인덱스가 없을 경우 통계 정보만 가지고 예측하기 때문에 오차가 크다
- 인덱스가 있어도 범위가 클 경우 인덱스 다이브를 포기한다.

### filtered
- 인덱스로 찾고 거기서 필터링 되는 비율이다.
- 스토리지 엔진이 인덱스를 통해서 데이터를 넘기면 실행 엔진이 걸러낸다.
- 이 값이 낮으면 실행 엔진이 버리는 비율이 높다는 것이다.
- 즉, 불필요한 행이 많다는 것

### extra
- Using index 긍정신호
	- 커버링 인덱스인 경우, 인덱스에 원하는 정보가 다 있는 경우이다.
- Using where 중립신호
	- 추가 필터링한 경우이다.
	- 경우에 따라서 스토리지 엔진에서도 필터링한다.
- Using filesort 경고신호
	- CPU를 사용해서 정렬한다.
	- 정렬 버퍼에 올려두고 작업하는데 메모리가 부족하면 디스크를 사용하기 때문에 극도로 느려진다.
	- 인덱스로 회피할 수 있는지 확인해본다.
- Using temporary 위험신호
	- Group By 등의 작업을 할 경우 임시 테이블을 만드는데 메모리가 부족하면 디스크를 사용하기 때문에 극도로 느려진다.
	- 인덱스가 없는 상황에서 group by 와 order by 를 섞어 쓸 때 자주 발생한다.
- Using index condition 긍정신호
	- ICP(index condition pushdown) 최적화 적용
