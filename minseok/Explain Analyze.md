- Explain 과 다르게 실제로 실행하고 예상과 실제 실행 결과를 보여준다.
- 출력 형식은 Tree 만 지원한다.
- 실제로 쿼리를 실행하기 때문에 주의해야한다. (무거운 쿼리 실행 시 DB 느려진다.)

### 실무 팁
- 데이터가 많다면 읽기 전용 레플리카에서 실행하거나 개발, 스테이징 환경 이용, 사람없는 시간 이용
- 혹은 Explain format=tree 이용

{실행 동작{} (cost=... rows=...) (actual time=A...B rows=... loop=...)
- 실행 동작
	- 어떤 연상을 수행 했는지
	- Table scan : Full Table Scan, type:ALL 에 해당
	- Index lookup : 동등 조건 인덱스
	- Index range scan : 범위 조건 인덱스
	- Filter : where 문 필터링, 통계 정보가 없다면 동등 조건을 10%로 가정해버림
	- Sort : 정렬, 가장 마지막 수행
	- Nested loop inner join : 조인문
		- 자식 노드가 있고 위부터 아래로 해석
		- 첫 번째 자식 : 드라이빙 테이블 (바깥 루프)
		- 두 번째 자식 : 드리븐 테이블 (안쪽 루프)
		- 이중 for 문이라고 생각하시오
		- 핵심 원칙 드라이빙이 작을 수록 드리븐의 인덱스가 있을 수록 빠르다
	- Single-row index lookup : 드리블 테이블 실행동작
	- Stream result : join 결과를 실시간으로 상위 노드로 올려준다. 파이프라인이다. 메모리 거의 사용 안 한다.
- 예상 정보 (옵티마이저 추정)
	- cost : 추정 비용, 단위는 없고 다른 실행 계획과 비교하는 상대적 수치, 옵티마이저가 내부적으로 사용하는 값
	- rows : 추정 반환 행의 수
- 실제 정보
	- actual time=A...B : 실제 소요 시간, 첫 번째 행 나온 시간(A), 마지막 행 나온 시간(B)
	- rows : 실제 반환 행의 수
	- loop : 이 단계가 실행된 횟수, 실제 총 시간 : actual time(두 번째값) * loops
- 루프 수
	- 해당 노드가 실행된 횟수
	- 조인에서 중요

### 사용법
1. Explain 으로 방향 잡기
	1. 쿼리를 실행하지 않기 때문에 빠르다.'
	2. 접근 유형, 인덱스, 예상 행 수 빠르게 확인
2. Explain Analyze 로 검증
	1. 예상 rows 와 실제 rows 를 비교한다.
	2. 차이가 크면 통계정보가 부정확하거나 옵티마이저가 잘못된 판단을 내릴 수 있다.
 - 차이가 작다면 실행계획이 정상이고
 - 차이가 크다면 통계 갱신이 필요하다.

### 조건재평가
- index range scan 했는데 왜 filter를 할까?
- 등호 조건은 보장되지만 범위 조건을 보장할 수 없다.
- ex) LIKE 'A%B' 같은 경우 인덱스를 통해 A는 보장하지만 그 뒤에 B가 나오는지는 보장할 수 없기 때문에 필터링한다.
- 하지만 Between 같은 확실한 조건도 필터링 하는데 그 이유는 이미 메모리에 올라왔기 때문에 거의 비용이 안들어가서 그렇게 MySQL을 설계를 한거다.
- Filter 할 때 스토리지 엔진에서 읽어들인 레코드를 MySQL 서버로 전달하는 오버헤드가 포함되어서 시간이 오래걸리는 것 처럼 보인다.

### 핵심 포인트
1. 명확한 드라이빙 선택
	1. 조인 성능을 높이기 위해서 필터링 조건이 명확하게 걸린 테이블 먼저 스캔
	2. 크기가 작은 테이블 선택
2. 병목은 Index lookup (join)
3. Top-N Sort 최적화 덕분에 정렬은 거의 공짜
4. 예상과 실제의 차이 - 데이터 편중 때문에 다르다.
