- Explain 과 다르게 실제로 실행하고 예상과 실제 실행 결과를 보여준다.
- 출력 형식은 Tree 만 지원한다.
- 실제로 쿼리를 실행하기 때문에 주의해야한다. (무거운 쿼리 실행 시 DB 느려진다.)

### 실무 팁
- 데이터가 많다면 읽기 전용 레플리카에서 실행하거나 개발, 스테이징 환경 이용, 사람없는 시간 이용
- 혹은 Explain format=tree 이용

{실행 동작{} (cost=... rows=...) (actual time=A...B rows=... loop=...)
- 실행 동작
	- 어떤 연상을 수행 했는지
	- Table scan : Full Table Scan, type:ALL 에 해당
	- Index lookup : 동등 조건 인덱스
	- Index range scan : 범위 조건 인덱스
	- Filter : where 문 필터링, 통계 정보가 없다면 동등 조건을 10%로 가정해버림
	- Sort : 정렬, 가장 마지막 수행
	- Nested loop inner join : 조인문
		- 자식 노드가 있고 위부터 아래로 해석
		- 첫 번째 자식 : 드라이빙 테이블 (바깥 루프)
		- 두 번째 자식 : 드리븐 테이블 (안쪽 루프)
		- 이중 for 문이라고 생각하시오
		- 핵심 원칙 드라이빙이 작을 수록 드리븐의 인덱스가 있을 수록 빠르다
	- Single-row index lookup : 드리블 테이블 실행동작
	- Stream result : join 결과를 실시간으로 상위 노드로 올려준다. 파이프라인이다. 메모리 거의 사용 안 한다.
- 예상 정보 (옵티마이저 추정)
	- cost : 추정 비용, 단위는 없고 다른 실행 계획과 비교하는 상대적 수치, 옵티마이저가 내부적으로 사용하는 값
	- rows : 추정 반환 행의 수
- 실제 정보
	- actual time=A...B : 실제 소요 시간, 첫 번째 행 나온 시간(A), 마지막 행 나온 시간(B)
	- rows : 실제 반환 행의 수
	- loop : 이 단계가 실행된 횟수, 실제 총 시간 : actual time(두 번째값) * loops
- 루프 수
	- 해당 노드가 실행된 횟수
	- 조인에서 중요

### 사용법
1. Explain 으로 방향 잡기
	1. 쿼리를 실행하지 않기 때문에 빠르다.'
	2. 접근 유형, 인덱스, 예상 행 수 빠르게 확인
2. Explain Analyze 로 검증
	1. 예상 rows 와 실제 rows 를 비교한다.
	2. 차이가 크면 통계정보가 부정확하거나 옵티마이저가 잘못된 판단을 내릴 수 있다.
 - 차이가 작다면 실행계획이 정상이고
 - 차이가 크다면 통계 갱신이 필요하다.

### 조건재평가
- index range scan 했는데 왜 filter를 할까?
- 등호 조건은 보장되지만 범위 조건을 보장할 수 없다.
- ex) LIKE 'A%B' 같은 경우 인덱스를 통해 A는 보장하지만 그 뒤에 B가 나오는지는 보장할 수 없기 때문에 필터링한다.
- 하지만 Between 같은 확실한 조건도 필터링 하는데 그 이유는 이미 메모리에 올라왔기 때문에 거의 비용이 안들어가서 그렇게 MySQL을 설계를 한거다.
- Filter 할 때 스토리지 엔진에서 읽어들인 레코드를 MySQL 서버로 전달하는 오버헤드가 포함되어서 시간이 오래걸리는 것 처럼 보인다.

### 핵심 포인트
1. 명확한 드라이빙 선택
	1. 조인 성능을 높이기 위해서 필터링 조건이 명확하게 걸린 테이블 먼저 스캔
	2. 크기가 작은 테이블 선택
2. 병목은 Index lookup (join)
3. Top-N Sort 최적화 덕분에 정렬은 거의 공짜
4. 예상과 실제의 차이 - 데이터 편중 때문에 다르다.

### Top - N 최적화
- limit input to 10 row(s) per chunk > 최적화 했다는 뜻

- 조회 결과를 전부 정렬하고  Top N 을 뽑는 건 심각한 단점이 있다
1. 알 필요없는 순위까지 계산한다.
2. 메모리 사용량이 많다 > 메모리가 부족해서 디스크를 사용하게 된다면 최악의 상황이 된다.(filesort on disk)
3. 시간 복잡도가 커진다. O(N logN)

#### Top - N Heap
- 상위 N 개를 고정적으로 메모리에 쥐고 나머지는 버리는 최적화 방법
- 비교한 행이 상위 N 개에 들어오지 못하면 바로 버린다.
- 디스크 스필(disk spill) 을 방지한다. (메모리가 할 일을 디스크로 넘기는 것 > 속도가 많이 느려짐)
1. N의 크기가 충분히 작아야 한다.
2. offset이 없거나 작아야 한다.
3. 정렬한 레코드의 크기가 정렬 버퍼보다 작아야한다.

### 파이프라인 모델 최적화
- 각 노드들은 작업이 모두 끝난 뒤 다음 노드로 데이터를 넘기는 것이 아니다.
- DB에서 한 행씩 레코드를 넘겨주면 처리하고 바로 다음 노드로 넘긴다.

##### My SQL 은 파이프라인(pull / iterator) 모델
- 각 노드는 반복자다.
- 부모가 다음 행 줘(Read()) 라고 요청(Pull()) 하면 자식이 한 행만 만들어서 위로 올린다.
- 정렬, 그룹, 임시 테이블 이런 작업은 Stream 을 할 수 없고 모든 작업이 끝날 때까지 기다린다 (Breaker)

##### 장점
1. 메모리를 아낀다. (중간 버퍼를 아낀다)
2. 첫 결과가 빨리 나온다.
3. 조기 종료가 가능하다.
4. 메모리의 한계에 안 걸린다.
5. 노드끼리의 결합이 단순해진다.

- SQL tool 은 stream 방식으로 전달 받은 데이터를 바로바로 보여주지만 어플리케이션은 메모리에 모든 결과가 올라와야 첫 행을 읽을 수 있다.
- 어플리케이션에서도 커서 기반 스트리밍으로 기술적으로 구현 가능하다.
1. DB 커넥션이 고갈될 위험이 있다.
2. 리소스 해제가 까다롭다. (리소스 누수 가능성)
3. ORM 및 프레임워크 메모리 누수 부하
- > 따라서 실무에선 거의 안 쓰고 배치, 페이징 처리로 해결한다.

### 예상 vs 실제
- 예상 결과 행과 실제 행이 차이나는 이유
1. 인덱스 다이브의 한계 (근사치 추정)
2. 통계정보가 오래된 경우
	1. Analyze Table [테이블명] 로 통계정보 최신화
	2. 8.0~ 버전부턴 락 관련 문제가 없다.
3. 데이터 분포의 편향
	1. 옵티마이저는 기본적으로 모든 데이터는 균등하게 분포하고 있다고 가정한다. (균등 분포 가정)

#### 오차
1. 오차가 2~3배 정도
	1. 정상 범위
2. 수 십 ~ 수 백배
	1. Analyze Table 로 최신화
3. 특정 조건의 값에 대해서만 유독 예측 오차가 심한 경우
	1. 인덱스가 없는 컬럼의 데이터 분포 편향으로 옵티마이저의 '균등 분포 가정' 이 무너졌다.
	2. 인덱스가 있는 컬럼은 히스토그램이 무시된다.
	3. 히스토그램을 생성하여 밀도 지도를 만든다.
