### 저장 프로시저 (Stored Procedure)
- 이름이 부여된 일련의 SQL 묶음
- 파라미터를 받거나 If, Loop 같은 제어문을 사용할 수 있다.

### 저장 함수 (Stored Function)
- 특정 계산을 수행하고 반드시 '하나의 값'을 반환하는 프로그램이다.

### 트리거 (Trigger)
- 특정 테이블에 특정 이벤트 발생 시 자동 실행되도록 약속된 프로그램 (Insert, Update, Delete)

이러한 프로그래밍 기능들은 과거 어플리케이션 서버 성능이 낮고 네트워크가 속도가 낮던 시절 여러번 쿼리를 보내기 보단 프로시저를 한 번 실행하는 방식으로 사용되었다.

하지만 최근 실무에서는 거의 사용하지 않는다.

### 단점
1. 유지보수의 어려움
	1. 비즈니스 로직이 DB에 들어가면 전체 시스템 로직이 어플리케이션과 DB에 흩어져 버린다. 이는 유지보수의 어려움을 초래한다.
	2. 버전관리가 어려워진다. Git 과 같은 버전 관리 프로그램을 사용하기 까다롭고 관리 포인트가 늘어난다.
2. 성능 및 확장성
	1. 과거엔 DB 서버가 가장 좋은 컴퓨터였다. 따라서 DB 서버에 일을 몰아줬다.
	2. 모든 비즈니스 로직이 DB에 집중되면 과부하가 일어나 병목현상이 생긴다.
	3. 현대적 웹 서비스는 수평적 확장에 유리하게 설계된다. 즉, 사람이 몰리면 비교적 저렴한 어플리케이션 서버를 증설한다. 하지만 DB는 상대적으로 수평적 확장이 어렵고 수직적 확장도 한계가 있을 뿐더러 비싸기 까지 하다.
3. 특정 DB 제조사에 대한 종속성
	1. Oracle, MS, Postgres, MySQL 전부 각기 다른 DB 프로그래밍 언어를 가지고 있다.
	2. 만약 DB 를 변경하게 된다면 감당할 수 없는 비용을 지불해야 할 것 이다.

### 현대의 대안 : 명확한 역할 분리
- App
	- 비즈니스 로직, 데이터 가공, 조건 처리, 절차 제어 등 모든 지능적 처리를 담당하고 표전 SQL을 사용한다.
- DB
	- 오직 데이터 저장, 조회, 무결성 보장, 트랜잭션 관리 등 DB 본연의 역할에 충실한다.
