- 데이터의 정확성, 일관성, 유효성을 유지하려는 성질

### 기본 제약 조건
1. Not Null
	1. 필수 데이터의 누락을 원천적으로 차단
2. Unique
	1. 중복 값 방지
	2. 해당 컬럼에 들어가는 모든 값은 테이블 내에서 반드시 고유해야한다.
3. Primary Key (기본 키)
	1. 행의 대표 식별자
	2. 테이블의 각 행을 고유하게 식별할 수 있는 단 하나의 대표 키
	3. Not Null 과 Unique 제약 조건을 모두 포함한다.
	4. 기본 키는 자동으로 인덱스(클러스터 인덱스)를 생성한다.
4. Default
	1. 기본값 설정
	2. 데이터 누락 방지
	3. 무결성 방지 보다는 편리한 기능의 개념

### 외래 키 제약 조건
- 참조 무결성 보장
- 유령 데이터를 막는 역할
1. 자식 테이블에 Insert, Update 할 때 부모 테이블에 존재하지 않는 값을 넣으려는 시도를 막는다.
2. 부모 테이블에서 Delete, Update 할 때 자식 테이블에 삭제, 변경하려는 데이터가 있다면 막는다

삭제하려면 자식 테이블을 지우고 그 후 부모 테이블을 지운다.

On Delete / On Update 옵션
1. Restrict (기본 값) : 자식 테이블에 참조하는 행이 있으면 부모 테이블의 행을 삭제/수정할 수 없다.
2. Cascade : 부모 테이블의 행이 삭제/수정되면, 그를 참조하는 자식 테이블의 행도 함께 자동으로 삭제/수정된다.
3. Set Null : 부모 테이블이 삭제/수정되면, 자식 테이블의 해당 외래 키 컬럼의 값을 Null 로 설정한다. (단, 이 옵션을 쓰려면 자식 테이블의 외래 키 컬림이 Null을 허용)

Cascade 는 위험해서 실무에서 거의 사용하지 않는다. 어플리케이션에서 명시적으로 삭제하는 방법을 선호한다. (자식 테이블 Delete 하고 부모 테이블 Delete 하는 식으로)

## Check 제약 조건
- 특정 컬럼에 들어갈 수 있는 값의 범위나 조건을 직접 지정하여, 한층 더 강화된 비즈니스 규칙을 적용하고 싶을 때 사용하는 조건

### 실무 팁
- 요즘 대세는 대부분의 비즈니스 로직과 유효성 검사를 애플리케이션에서 직접 처리하는것.
- 훨씬 유연하고 테스트가 쉽기 때문
- 이런한 이유로 데이터베이스의 Check 제약 조건은 잘 사용하지 않는 추세
- 만약 사용한다면 간단하지만 절대 값이 바뀌면 안 되는 핵심 데이터에만 '최후의 방어선' 으로 사용
- 제약 조건을 거는 걸 권장한다. (데이터 무결성 깨지는 경우를 너무 많이 봤다)
