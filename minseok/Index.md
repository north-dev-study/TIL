## Index 란?
- 특정 컬럼을 정렬해서 저장하고 이를 통해 원본 데이터에 빠르게 접근할 수 있는 특별한 목차이다.

### Full Table Scan
1. 데이터 조회가 느려지는 원인이다.
2. 말 그대로 테이블을 처음부터 끝까지 전부 조회하는 것이다.
3. 디스크 IO 병목현상이 일어날 수 있다.
4. O(n) : Big O 데이터가 늘어날 수록 비례해서 느려진다.

### Full Table Scan 방지 실무적 관점
1. 인덱스 활용
	1. Where 절에 자주 사용하는 컬럼에 Index를 생성한다.
2. 실행계획 확인
	1. 의도치 않은 Full Table Scan 이 발생하는지 확인한다.
3. 작업시간 분리
	1. 대용량 데이터 Full Table Scan이 필요할 경우 새벽 시간을 이용한다. (새벽에 실행되는 쿼리 작성)

### 트리 자료 구조
- 트리는 부모 노드와 자식노드로 구성된다.

1. 이진 탐색 트리
	1. 왼쪽 자손이 더 작은 값을 가지고 오른쪽 자손이 더 큰 값을 가진다.
	2. 한 번에 탐색할 절반을 날려 버린다.
	3. O(log n) 
	4. 데이터의 크기가 클 수록 효과적이다.
	5. ★데이터를 정렬한 상태로 보관해두어야 한다!
	6. 최악의 경우 Full Table Scan과 동일하다. > 이를 보완하기 위해 밸런스 트리 등장
	7. 인덱스에 쓰이는 B-Tree는 밸런스 트리의 한 종류
2. 순회
	1. 중위순회
		1. 같은 방향으로만 노드를 처리한다.
		2. ex) 왼쪽 노드를 처리하고 원래로 돌아온다
		3. 오름차순, 내림차순 구현가능하다.

### PK, FK, Unique Key
1. 이 제약조건들은 자동으로 인덱스를 생성한다.
2. PK와 FK는 그렇다 해도 Unique Key는 왜? > 테이블에 Insert 나 Update 하려는 값이 중복되었는지 조회를 해야하기때문이다.

### 실행계획
- Explain [쿼리]

1. type
	1. ALL : Full Table Scan
	2. ref : =, join 과 같은 동등 조건에서 인덱스 사용
	3. range : between, >, < 과 같은 범위 조건에서 인덱스 사용
2. key
	1. 쿼리를 실행할 때 사용한 인덱스
3. rows
	1. 탐색할 것으로 예상되는 행의 수
4. filtered
	1. 조건에 의해 필터링 되고 남을 비율
5. Extra
	1. Using where : 데이터를 가져온 후에 where 사용
	2. Using index condition : 인덱스 사용

### 범위 조건
- 처음 하나만 이진 탐색으로 찾고 그 이후는 연속적으로 탐색한다 (정렬되어있기 때문에 가능하다)

### 정렬
- 비용을 많이 잡아먹는 작업이다.
- Order by 에 인덱스 컬럼을 사용할 경우 옵티마이저가 정렬 작업을 생략해버린다 (인덱스 자체가 원래 정렬되어 있기 때문에)
- 단일 컬럼 인덱스에선 역방향도 가능하다.
- 정방향 스캔이 역방향 스캔보다 미세하게 빠르다. (컴퓨터 하드웨어의 미리읽기 때문)
- 내림차순 인덱스를 만들 수 있다. (단일 컬럼 인덱스는 큰 차이 없다)
- 복합 인덱스에선 오름차순, 내림차순 인덱스가 중요해진다. (정렬 순서도 이에 맞게 적용해야 인덱스 효과를 본다.)

### LIKE
- 와일드 카드가 맨 뒤에 위치해야 인덱스를 사용할 수 있다.
- 와일드 카드 앞 부분만 이진 탐색하고 그 이후로는 범위 조건과 같이 연속적으로 탐색한다.
- 와일드 카드가 앞에 있으면 Full Table Scan이 일어난다.
- 필요한 경우 Full - Text Seach 라는 전문 검색 기능 적용

### 인덱스 손익분기점
- 인덱스가 있다고 무조건 사용되지는 않는다.
- 옵티마이저가 통계를 비교 후 Full Table Scan이 낫다고 판단할 수도 있다.
- 인덱스 사용 시 검색 대상은 확실히 줄어들지만 테이블에 흩어진 데이터에 접근해야한다.
- 인덱스를 사용하는 비용 : 인덱스 탐색비용 + 인덱스에서 찾은 주소로 원본테이블 접근 비용 (랜덤 I/O)
- FTS 비용 : 순서대로 읽는 비용(순차 I/O)
- 일반적으로 전체 데이터의 20~25% 이상을 조회하는 쿼리는 FTS이 더 효율적이라고 한다.

### 랜덤 I/O가 느린 이유
#### 순차 I/O
- HDD의 경우 디스크 헤더가 거의 움직이지 않고 연속적으로 읽어온다.
- SSD의 경우 하나의 큰 명령어를 실행한다.
#### 랜덤 I/O
- HDD의 경우 디스크 헤더가 물리적으로 이동해야 하기 때문에 (탐색시간이 추가된다)
- SSD의 경우 작은 명령어를 여러 번 실행해야하기 때문에 SSD 컨트롤러에 오버헤드 발생

- 따라서 Index 사용 시 디스크의 여러 위치를 오가는 랜덤 I/O 를 유발할 가능성이 커진다.
- 데이터가 소량일 경우 그냥 인덱스를 안 쓸 수도 있다.

### 커버링 인덱스
- 인덱스에 조회에 필요한 데이터가 모두 있다면 원본 테이블에 접근할 필요가 없다. (랜덤 I/O 삭제) -> 성능 비약적 상승
- 인덱스에 조회에 필요한 모든 데이터가 있는 것이 커버링 인덱스
- 장점 : 압도적인 Select 성능 향상 (랜덤 I/O 제거), 특히 Count 쿼리 최적화 (인덱스만 스캔하면 되기 때문)
- 단점 : 저장공간 증가, 쓰기 성능 저하 (인덱스도 같이 수정해야 하기 때문)
- 조회가 빈번하고 쓰기가 상대적으로 적은 테이블에 적용하는 것이 좋다.
- 성능 저하가 발생하는 특정 쿼리를 튜닝하기 위한 "비장의 무기"로 사용하는 것이 좋다.

### 복합 인덱스 !!!!!
- 다중 컬럼 인덱스 라고도 한다
- 컬럼의 순서가 매우 중요하다.
- 선행 컬럼으로 정렬하고 그 안에서 후행 컬럼으로 정렬하는 개념이다. (order by 랑 같다)
- 따라서 후행 컬럼만으로 정렬되어있는게 아니기 때문에 후행 컬럼만으로 인덱스를 사용할 수 없다. 반드시 선행 컬럼이 있어야 한다. 이를 '인덱스 왼쪽 접두어 규칙 (Index Left-Prefix Rule)' 이라고 한다.

#### 복합 인덱스 대원칙 !!!!!
1. 인덱스는 순서대로 사용하라!
	1. 후행 컬럼을 사용하고자 한다면 선행 컬럼들이 반드시 있어야한다.
2. 등호(=) 조건은 앞으로, 범위 조건(<,>)은 뒤로 !
	1. 선행 컬럼이 범위조건일 경우 선행 인덱스를 통과할 경우 선행 컬럼은 정렬 되어있지만 후행 컬럼은 정렬되어있지 않은 데이터셋을 받게 된다. 이는 후행 컬럼부터는 인덱스를 효율적으로 사용할 수 없게 됨을 의미한다.
	2. 범위 조건이 걸리는 순간 인덱스가 깨진다고 생각하자
	3. 이를 파훼하기 위해 실무에서는 범위조건 대신 IN 조건을 사용할 수 있다! (여러 개의 동등 조건으로 인식하기 때문에 따로 따로 인덱스를 탄다, 대신 다양성이 적은 컬럼에 쓰는게 좋다)
3. 정렬도 인덱스 순서를 따르라!
	1. 정렬은 비용을 많이 지불해야 하는 작업이다. 따라서 filesort를 피하게 된다면 성능에 결정적인 영향을 미칠 수 있다.
	2. 인덱스를 이용한다면 자연적으로 정렬이 됨으로 이를 이용하자!

### 인덱스 설계 가이드
- 핵심 원칙 : 카디널리티 (Cardinality)
	- 높다 : 중복되는게 적다.
	- 낮다 : 중복되는게 많다.
- 인덱스는 카디널리티가 높은, 즉 식별력이 좋은 컬럼이 효율적이다.
1. Where 조건에 자주 사용되는 컬럼
2. Join 절의 연결고리 컬럼
3. Order by 에 자주 사용되는 컬럼

### 인덱스 단점, 주의사항
1. 저장공간
	1. 한 인덱스 당 대략 원본테이블의 10% 라고 하기 때문에 인덱스를 많이 만들 수록 많은 저장공간을 사용하게 된다.
2. 쓰기 성능 저하(Insert, Update, Delete)
	1. 원본 테이블과 동시에 인덱스도 수정해야하기 때문에 비용이 많이 든다.(밸런스도 맞춰야 한다.)
