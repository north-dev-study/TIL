### 대용량 트래픽 예매 시스템 특징
---
- 동시 트래픽이 많음
- 순서 보장
- 초과 예매 X
- 중복 예매 X

### 아키텍쳐 설계
---
![[../assets/Pasted image 20260718203536.png]]


보통 3단계로 설계

**1단계 : 대기열 등록**
- 인메모리 시스템에 등록

**2단계 : 예매 입장**
- 스케쥴러가 대기열에서 순서대로 예매로 입장

**3단계 : 예매 처리**
- 실제 RDB에 들어가도록 처리


- 요즘은 Redis가 대기열에 적합한 솔루션이라 많이 사용
Redis의 ZSET(정렬 자료구조) 를 사용
Redis는 클러스터로 준비해야

- 로그인 전 예매 접속 > API > UUID 식별자 값 생성 > Redis에 UUID 식별자로 ZSET에 timestamp와 같이 등록(timestamp로 선착순 정렬 가능) > 다음 요청부터는 UUID를 갖고 들어옴

- 대기열에서는 주로 3가지 기술로 대기처리
**폴링** - 가장 보편적으로 사용
**SSE**
**웹소켓** - 네트워크 단에서 순단이 있을수도 있음


- Redis에서 저장된 값을 백단에서 스케쥴러를 돌면서 앞에서부터 몇명까지 가져감(명수는 예약처리 시스템의 TPS 보다 조금 더 여유있게 가져감. 만약 초당 100건의 트랜잭션을 처리할수있으면 6~70건을 가져감). 이 예매가능인원은 Redis 내부에 Active user로 저장해둠

- Redis는 G랭크, G카드로 내 앞에 몇명남았는지를 빠르게 가져갈수있음

- 주기적으로 사용자가 active한지를 체크하고, Redis의 Active User안에 들어가있으면 예매 과정을 시작함

- 예매 시스템에서 중복 예매가 안되도록 RDBMS의 락을 쓰거나할수도있지만 그럼 부하가 걸릴수있기떄문에 Redis의 Atomic한 연산을 이용해서 동시성 제어를 함
- Lua script로 로직을 짜서 멀티 스레드 환경에서도 원자적 작업을 실행할수있게함
- 예매 가능 좌석은 실시간으로 Redis에 넣어놓고, Redis에서 잔여좌석 있음 ok 사인을 주면 API에서 성공처리 로직을 실행함
- 예약 성공 후에는 바로 RDB에 넣을수도 있고, or 부하방지를 위해 MQ를 넣을수도 있음. MQ 뒤에 worker가 빼서 DB에 넣음
- KTX는 결제까진 안하고, 좌석예매까지 넣음. 이런식으로 최대한 기능을 나누는게 좋음
